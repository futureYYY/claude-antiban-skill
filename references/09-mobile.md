# 09 · 手机端（真机）

> **如果配手机是为了走 Google Play 订阅**：先把本文第 9 节的验收清单全部跑过，再回 `04-account-and-payment.md` 付款。出口 IP 和电脑不一致时不要订阅。

> 电脑端是 AdsPower 指纹环境，手机端没有等价物。这一节只讲**真机能做到什么、做不到什么**，以及实测踩出来的坑。

---

## 0. 先划边界：真机做不到指纹隔离

| 能控 | 怎么控 |
|---|---|
| 出口 IP | 手机上装 Clash 类客户端，复刻电脑那条链 |
| 时区 | 关自动，设为出口所在地 |
| 语言 | **只改 Claude 应用级语言**，不动系统 |
| 定位 | 关闭 |
| 账户数量 | **一号一机** |

| 改不了 | 后果 |
|---|---|
| 机型、序列号、传感器、GPU、内核 | 无法伪装成另一台设备 |

**结论：手机端不是「一台机器跑多个环境」，而是「一台机器绑一个账号」。** 想多号，就得多设备或专用云机。

---

## 1. 客户端与链式

选支持 `dialer-proxy` 的客户端（Clash Meta for Android / CMFA 实测可用），才能复刻电脑那条「本机 → 中转 → 出口」的链。

**做法**：从电脑的 `clash-verge.yaml` 里抽出**两个节点**——

1. 出口节点（类型 ss，带 `dialer-proxy: '<中转节点名>'`）
2. 它的 `dialer-proxy` 指向的那个中转节点

再加一个 `select` 组和一个 `MATCH` 兜底，就能在手机上跑出同一条链。

**判据（关键，不要看出口 IP）**：在手机上执行 `ss -tn`，应该**只看到连向中转入口**的连接，**没有一条直连出口服务器**。

```
<本机内网IP>:xxxxx  →  <中转入口IP>:<中转端口>     ← 应全是这种
                       （不应出现 <VPS_IP>:<SS_PORT>）
```

只看出口 IP 等于没验——出口对了也可能没成链。

## 2. 导入配置的五个坑

### 坑 1：VPN 开着的时候导入，会静默失败

App 自己下载配置文件的请求，同样会被 `MATCH` 规则送进代理隧道 —— 于是它去连 `127.0.0.1:端口` 时被转给了出口服务器，必然失败，界面上只表现为「保存了但列表没新增」。

**做法：先停 VPN，再导入，导入完成后再启动。**

### 坑 2：配置里必须让内网直连

即便停了 VPN，只要配置里有 URL 反代之类的本地服务，也可能被兜底规则吞掉。加四条最稳：

```yaml
rules:
  - IP-CIDR,127.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,172.16.0.0/12,DIRECT,no-resolve
  - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
  - MATCH,<组名>
```

### 坑 3：中转入口是域名时，DNS 会死循环

链式的第一跳如果是**域名**（订阅提供的节点常见），客户端要解析它才能连；而解析请求本身又被送进代理 → `dns resolve failed`。

**做法**：在配置里加 `hosts:`，把中转入口域名钉成解析出来的 IP：

```yaml
hosts:
  <中转入口域名>: <该域名解析到的IP>
```

**代价**：入口 IP 一变（机场换入口是常事），这份配置就失效。所以手机上**至少留一份独立可用的备用订阅**，主配置挂了还能上网。

### 坑 4：连续导入会产生多个同名草稿

用深链（`clash://install-config?url=...`）或反复点保存，列表里会堆出好几个同名的「新配置」，界面上不带 URL，分不清谁是谁。

- **导入完成后立刻改名**（点卡片右侧按钮 → 编辑 → 名称）
- 删除时要小心：**删到正在运行的那份，VPN 会立刻停止**

### 坑 5：批量推配置可以用 adb，但要按顺序

比手点快得多的做法（需要 USB）：

1. 电脑起一个临时 HTTP 服务，把 yaml 放在目录里
2. `adb reverse tcp:<端口> tcp:<端口>`，让手机能用 `127.0.0.1` 访问电脑
3. `adb shell am start -a android.intent.action.VIEW -d 'clash://install-config?url=http://127.0.0.1:<端口>/x.yaml'`
4. 导入完成后**移除端口映射、关掉临时服务**

## 3. 系统设置怎么对齐

| 项 | 值 | 做法 | 判据 |
|---|---|---|---|
| 时区 | 出口所在地 | 关自动时区，手动选 | `getprop persist.sys.timezone` |
| Claude 语言 | `en-US` | **只改应用级**，不动系统 | `cmd locale get-app-locales <包名>` |
| 定位 | 关 | 系统开关 | `settings get secure location_mode` = 0 |

**不要切整个系统语言**：结果是半英半中（国产 App 没有英文包），而且银行/支付类 App 可能因为「环境变化」要求重新验证，收益远小于麻烦。

## 4. 关 IPv6（改 APN，不是改客户端）

IPv6 是这套东西最容易被忽略的泄漏面：手机卡普遍下发公网 IPv6，客户端若只接管 IPv4，浏览器会优先走 v6 露真实地址。

**做法**：把**上网 APN** 的协议改成 `IP`（仅 IPv4），漫游协议一起改。

**红线：不要动 IMS APN。** 运营商的 VoLTE 走 IPv4/IPv6 双栈，把 IMS 改成 IPv4 可能导致电话、短信不可用（很多地区已无 2G/3G 兜底）。

**判据**：

- 系统层：`dumpsys telephony.registry` 里，**上网那条 PDN 只有 IPv4 地址**；IMS 那条仍带 v6 是**正常**的
- 应用层：手机执行 `curl -6 https://api64.ipify.org` 返回空

改完需要重启或重建数据连接才生效。

## 5. 四项泄漏自检（手机版）

| 项 | 怎么查 | 过线标准 | 不过线说明 |
|---|---|---|---|
| IPv4 出口 | `curl -s https://api.ipify.org` | = 你的服务器 IP | 走了别处或没成链 |
| IPv6 | `curl -6 https://api64.ipify.org` | **返回空** | 仍在分配 v6 |
| DNS | 在浏览器开解析检测页 | 解析器显示出口国 | 出现本地运营商解析器 |
| WebRTC | 在浏览器开 WebRTC 检测页 | **只出现 `172.19.x` 这类私有地址** | 出现公网地址 = 真泄漏 |

### WebRTC 那条要单独说

- 泄漏的直接原因是**节点没开 `udp: true`**：WebRTC 用 UDP 打 STUN，客户端不接这条 UDP，浏览器就用底层网络出去了
- 补上 `udp: true` 后若**仍拿不到公网候选**（只剩 `172.19.x`），说明 UDP 回程断在中转节点（机场常关 UDP）
- 这种状态**是安全的**：拿不到公网候选 = 泄漏不了。**不要为了「检测页好看」把 UDP 改成直连出口服务器**——那会把真实 IP 写进服务器日志，链式就白做了

## 6. 「不开梯子就断网」在安卓上不可靠

想复刻电脑那种 fail-closed，Android 有 `始终开启 VPN` + `阻止未使用 VPN 的连接` 两个开关。实测：

- 用命令写入 `always_on_vpn_app` / `always_on_vpn_lockdown` 后，**系统值确实变了**
- 但手机重启后客户端**没有被拉起**，而且网络照常可用（默认网络仍是普通移动/WiFi 网络，状态是 `NOT_VPN`）
- 也就是说：**这两个值在某些 ROM 上不被真正执行**

**结论：不要依赖「不开梯子就没网」。** 要靠行为纪律 + 下面第 8 节把 App 后台封死。

---

## 7. 裸网时 Claude 的真实表现

不开梯子直接请求 `claude.ai`，实测返回：

```
HTTP/1.1 302 Found
Location: https://claude.com/app-unavailable-in-region
```

含义有两层：

1. **域名本身是通的**（不是被墙），进不去是因为**按 IP 判定地区**
2. **每个请求都会判定**，不是偶尔抽查

所以「不开梯子能不能用」这个问题不存在——用不了。真正要关心的是：**这次被拒绝的请求里，有没有带你的身份**。

## 8. 真正的高风险：带身份的请求

| 来源 | 带什么 | 风险 |
|---|---|---|
| App 后台请求 | 账号 token | 🔴 高——直接是「这个账号在中国」 |
| 浏览器已登录状态 | cookie | 🔴 高 |
| 浏览器匿名访问 | 只有 IP | 🟡 低 |

App 会在后台定时刷新，**不需要你主动打开**。所以不开梯子时必须把它的后台封死。

### 三条命令（USB 连电脑执行，<UID> 用 `pm list packages -U` 取）

```
cmd netpolicy add restrict-background-blacklist <UID>
cmd appops set <包名> RUN_ANY_IN_BACKGROUND ignore
am force-stop <包名>
```

**验证**：

- `ps -A | grep <包名>` → 无进程
- `cat /proc/net/tcp | awk '$8==<UID>'` → 无连接
- `dumpsys netpolicy | grep UID=<UID>` → 出现 `REJECT_METERED_BACKGROUND`

**边界**：这两条只封**后台**。你手动点开 App，前台数据是放行的，会立刻用当前网络（没开梯子就是本地 IP）请求一次。所以纪律是：**不开梯子，别点它。**

### 回滚

```
cmd netpolicy remove restrict-background-blacklist <UID>
cmd appops set <包名> RUN_ANY_IN_BACKGROUND allow
```

## 9. 手机端验收清单

- [ ] `ss -tn` 只看到连向中转入口，无直连出口服务器
- [ ] 出口 IP = 你的服务器
- [ ] `curl -6` 返回空
- [ ] 解析器显示出口国
- [ ] WebRTC 只出现 `172.19.x` 之类私有地址
- [ ] 时区 = 出口所在地，自动时区关闭
- [ ] Claude 应用语言 = `en-US`（系统语言未动）
- [ ] 上网 APN 协议 = 仅 IPv4，IMS APN 未动
- [ ] App 后台数据 / 后台活动已限制（不开梯子时）
- [ ] 至少留一份独立可用的备用订阅

## 10. 常见误读

| 说法 | 实际情况 |
|---|---|
| 手机上装个指纹浏览器就能多账号 | 真机无 root 做不到；机型、序列号改不了，只能一号一机 |
| 出口 IP 对了就说明链成了 | 要看**服务器侧**和手机侧的两端证据，中间可能早断了 |
| WebRTC 检测页报错就是配置坏了 | 拿不到公网候选恰恰说明没泄漏 |
| 开了「阻止未使用 VPN 的连接」就万无一失 | 部分 ROM 不执行这个设置，实测重启后仍能上网 |
| 切系统英文更「像美国人」 | 半英半中，还可能触发银行类 App 重验，收益很低 |
| 顺手点开 App 没事 | 前台请求是放行的，会立刻用本地 IP 发一次 |
